## §1. Purpose and Rules

### §1.1. Purpose

This register is the single inventory of open architectural and game-design decisions in the v4 specifications. Its job is to:

- make every open question visible in one place;
- preserve the original document IDs while removing register-level duplication;
- classify each question by what it blocks (`BLOCKER` / `PROTOTYPE` / `CONTENT` / `DEFERRED`);
- separate decisions required for the **first vertical slice (P03–P05)** from later production blockers;
- give the project owner an ordered decision queue.

**P01 does not implement decisions.** A question being listed here grants no permission to implement a behaviour, and a suggested option being quoted here does not make it approved.

### §1.2. Source priority

When sources conflict, apply the project-wide priority order from the master plan:

1. The latest explicit decision of the project owner.
2. Positions marked **СОГЛАСОВАНО** in the target specifications.
3. Approved architectural decisions and ADRs.
4. The original game canon «Цикл 48».
5. Positions marked **ПРЕДЛАГАЕТСЯ** — as implementation options only.
6. Current code — evidence of actual implementation, never a reason to preserve old game rules.

### §1.3. Meaning of source statuses

| Status           | Meaning                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------- |
| **СОГЛАСОВАНО**  | Explicitly fixed by the original canon or confirmed by the project owner.                   |
| **ПРЕДЛАГАЕТСЯ** | A proposed option/engineering recommendation. Can change after prototyping. Not a decision. |
| **ОТКРЫТО**      | Requires an owner decision, a test/measurement, or game-balance work.                       |

### §1.3.1. Owner-decision updates

The statuses in §3 originally reproduce the source specifications as audited on 2026-11-17. A later explicit owner decision takes priority under §1.2. Where such a decision is recorded below, the register marks the linked issue rows as owner-approved; the source specification files remain unchanged in P01 and must be synchronized during the relevant implementation/contract task. This preserves the distinction between an approved semantic decision and an implemented/frozen wire schema.

### §1.4. Rules binding on the coding agent

1. The coding agent **does not decide game rules** and does not convert a proposal into canon.
2. A question present in this register is **not resolved** by being listed, classified or prototyped.
3. Prototypes may use values explicitly labelled `PROTOTYPE-ONLY`; such values must never silently become production rules or production configuration.
4. Original document IDs are immutable. Local register keys (`UNASSIGNED-*-L<line>`, `GROUP-*`) are register-local identifiers, **not** specification IDs.
5. Where a source lists options, the register quotes them; it never adds options of its own.
6. Absence of data is recorded as `NOT SPECIFIED` or `OWNER INPUT REQUIRED` — never filled by guesswork.
7. Spec text is not edited in P01. Contradictions are preserved and reported (§5).

## §3. Canonical Decision Register

### §3.0. Column legend and standing defaults

Each subsection below names its source document. Column meanings:

- **Anchor** — line(s) in the source document at the current audited snapshot; `§` denotes the enclosing section.
- **Question** — faithful short form; full text remains in the source.
- **Status** — source status. Default for every row: `ОТКРЫТО`.
- **Class** — `BLOCKER` / `PROTOTYPE` / `CONTENT` / `DEFERRED` (rules: §4).
- **Blocks** — exact scope: `slice` (P03–P05), `production <subsystem>`, `full lifecycle`. `—` for CONTENT/DEFERRED rows that block no implementation.
- **Impact** — consequence if the decision stays open.
- **Options** — only options literally present in the source; `нет` means the source lists none.
- **Proto?** — can a prototype or interface be built without the canonical decision: `YES` / `PARTIAL` / `NO`.
- **Cross-ref** — register group keys (`G*`) and original IDs describing the same decision.
- **Next action** — the concrete next step for the owner/team.

**Standing defaults** (stated once instead of repeating in every row): _Decision owner_ = project owner for all rows; _Required approval_ = owner-approved update of the source specification (plus ADR if the owner chooses to create an ADR structure); _Source status_ = `ОТКРЫТО` unless the row says otherwise.

Row-level IDs are immutable document IDs. `UNASSIGNED-*` keys are register-local and must not be cited as specification IDs.

## §4. Classification Rules

A single question receives exactly one class.

### BLOCKER

The decision blocks a safe implementation of a **named** capability or the transition to a **named** phase. Every BLOCKER row states what exactly is blocked:

- `first vertical slice` (P03–P05: one test room, authoritative movement, two browsers);
- `prototype` (a narrow experiment is impossible without the answer);
- `production implementation` (named subsystem cannot ship safely);
- `full game lifecycle` (a named phase cannot be completed end-to-end).

A question that only blocks a late optional mechanic is **not** a whole-project blocker and is not labelled as one.

### PROTOTYPE

The question can be answered by measurement, experiment or comparison **without** approving game canon. Each such row names:

- the hypothesis;
- what to measure;
- the minimal experiment;
- the comparison criterion;
- which part still requires the project owner.

### CONTENT

Production content questions: texts, floor profiles, authored data, assets, ability tables, fallback lines and similar material that does not have to be final to test base movement.

### DEFERRED

Not needed for the next vertical slice; can wait without architectural damage. `DEFERRED` is never used to hide a serious production blocker.

### Rule against over-blocking

BLOCKER means "cannot safely implement X". If X is a late optional feature, the class is `DEFERRED` or `CONTENT`, not `BLOCKER`.

### §6.1.1. Owner decision recorded — G1 (2026-11-19)

**Status: СОГЛАСОВАНО владельцем проекта для первого вертикального среза.**

**Decision:** use free directional keyboard movement with **WASD and arrow keys**.

Scope:

- The first vertical slice uses held-direction keyboard input.
- Click-to-move is not part of this slice.
- A combined click-to-move + directional mode is not part of this slice.
- This decision selects the input mode; it does not set character speeds, sprint rules, collision geometry, movement balance or permanent controls for later versions.

Contract consequences for the three linked source IDs:

1. **WS-03 — input model:** resolved as free directional movement. The P03–P05 slice is not to implement click-to-move as its movement mode.
2. **HC-02 — HOT/COLD input semantics:** resolved as held direction, not click-to-move or a destination/velocity command. The client samples the current directional state; the server derives movement using its own speed/rules and fixed simulation step. The illustrative `directionX`/`directionY` fields in `WORLD_SIMULATION.md` are a compatible candidate, not yet a frozen Zod schema.
3. **NET-02 — network input mode:** resolved as held-direction input. The movement message must fit the existing protocol semantics: `inputStreamId` + monotonically increasing `inputSequence`; repeated/stale sequences are rejected; key release/stop is represented explicitly; old movement inputs are not replayed after reconnect and a new input stream is created. The authenticated connection supplies actor identity.

**Protocol invariants carried forward from the specifications (not new choices):**

- Send movement intent, never a trusted final position or client-authoritative speed/acceleration.
- The server validates and normalizes the input, applies server-owned movement rules, and acknowledges the last processed input sequence.
- The client may predict its own movement and reconcile it against authoritative server state.

### §6.1.2. Owner decision recorded — G2 (2026-11-19)

**Status: СОГЛАСОВАНО владельцем проекта.**

**Decision:** adopt coordinate convention A for the v4 world-coordinate model and the first vertical slice. One world-coordinate unit equals one grid-cell side. Cell `(gx, gy)` occupies `[gx, gx+1) × [gy, gy+1)`; its center is `(gx+0.5, gy+0.5)`. `X` increases to the right and `Y` increases downward. The containing cell is obtained with `floor(x), floor(y)`.

**Precision decision:** entity world positions remain continuous fractional coordinates represented with ordinary TypeScript `number` values. Do not round positions to cell centers, snap movement to integer coordinates, introduce fixed-point coordinates, or apply an additional quantization layer. Cell lookup does not modify the world position. Coordinates must be finite and remain within the active World Pack / WorldSpace bounds. Collision tolerances are a separate geometry setting and are not coordinate quantization.

**Compatibility with G1:** WASD/arrows remain held-direction input. Right/left map to positive/negative X; down/up map to positive/negative Y. The client may predict using this convention, but the server remains authoritative. Snapshots and reconciliation preserve fractional world coordinates; they must not round positions to integer grid coordinates.

**Contract consequences:** `WS-02` and `UNASSIGNED-WSIM-L235` are resolved. P02–P05 must use this convention consistently in World Pack types, HOT movement, client transforms, scene snapshots and reconciliation. Exact shared TypeScript/Zod field names and wire structure remain P02/P05 work; this decision does not freeze the payload schema.

**Still open / not approved by G2:** collision algorithm (`HC-03`, subsequently decided by G3); production-wide collider shape (`WS-05`); navigation adjacency (`WS-06`); movement speeds and sprint/balance rules; input cadence, input lease and interpolation tuning.

G2 closes the coordinate convention and quantization questions only.

### §6.1.3. Owner decision recorded — G3 (2026-11-19)

**Status: СОГЛАСОВАНО владельцем проекта для первого вертикального среза.**

**Decision:** use swept-circle collision for server-authoritative movement in the first vertical slice.

Scope and required behaviour:

- The prototype represents the moving character by a circle/disc on the floor plane. Its collision radius is a configurable prototype parameter; it is not derived from sprite transparency or rendered dimensions.
- For each fixed HOT movement step (`dt = 0.05 s`), the server checks the swept movement trajectory against the tile-map collision geometry, not only the final position.
- The character must not tunnel through walls or other blocking geometry between ticks.
- When a collision blocks part of the requested displacement, the implementation may preserve the tangential component so the character can slide along the obstacle rather than stopping unnecessarily.
- Collision tolerance is centralized and configurable. The actual radius and numeric tolerance are calibrated through P04 test-room measurements; this approval does not invent final balance/physics numbers.
- The server remains the sole authority for collision resolution and the resulting position. Client prediction must use compatible geometry for presentation, then reconcile to the server snapshot.

**Contract consequences:** `HC-03` is resolved as the first-slice collision algorithm/basis. P04 must implement swept-circle collision against the server World Pack geometry and cover tunneling, wall contact, sliding and boundary behaviour with tests. The radius and tolerance are prototype configuration, not hard-coded scattered constants.

**Still open / not approved by G3:** the production-wide collider choice beyond this first-slice prototype (`WS-05`); 4- vs 8-neighbour Doll/navigation adjacency (`WS-06`); exact numerical radius/tolerance until measured; broader movement balance and other entity-specific collision rules.

G3 closes the collision-algorithm basis required for the first vertical slice. It does not settle every later spatial/navigation decision.
